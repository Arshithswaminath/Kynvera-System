HOW YOUR INFORMATION IS PROTECTED

Two keys to get in, and every room inside locked separately.

Five checkpoints stand between the public internet and your data. No one — not your staff, not ours, not anyone holding the database — can read a password. And every action is written down with a name and a timestamp.

THE WAY IN

Five checkpoints, in order

Every single request — opening a page, saving a form, uploading a photo — walks this same corridor before it touches anything. The technical name for each is in parentheses, for whoever needs it.

01

Front Door

Username + password, plus an optional second step: a 6-digit code from an authenticator app, like the ones banks use. Turning it on is a 3-step handshake — see a QR code, prove a live code works, then it's required every time. Turning it off needs your password again, and either way you get an email.

(login + TOTP multi-factor authentication)

02

Visitor Pass

Signing in issues a short-lived pass good for 1 hour, and a longer one good for 7 days that quietly renews it. Every pass is on a list, so a lost or stolen one can be cut off immediately, from anywhere.

(JWT access + refresh tokens, server-revocable sessions)

03

Corridor Sensors

Too many login attempts in a row locks that door for a while, slowing down password guessing. A hidden stamp on every form-submission has to match, so a malicious website can't secretly act on your behalf using your open session.

(rate limiting + CSRF protection)

04

Room Access

Your badge only opens rooms you're cleared for. Most staff see only the modules they're granted; the admin console needs the admin badge specifically.

(role-based access control)

05

Package Check

Anything brought in gets inspected: only the right kind of file for the job (photos for tickets, spreadsheets for bulk imports), nothing over the size limit, and no sneaky filenames that try to reach outside their folder.

(file-type validation, size limits, path-traversal protection)

THE RULES BEHIND THE DOORS

Password policy, and the protections that never switch off

Passwords

  • At least 8 characters, with upper case, lower case and a digit.
  • Stored only as an irreversible scramble — nobody can read the original, ever.
  • New accounts get a random one-time password, never a shared default.
  • A "forgot password" reply looks identical whether or not the account exists, so nobody can fish for valid staff emails.
  • Changing a password signs that person out of every other device immediately.

Always on, every page

  • The site cannot be secretly framed inside another website to trick a member of staff.
  • Browsers are told exactly what each file is, so a disguised file can't be misread as something else.
  • Encrypted connections are enforced — an unencrypted one is refused, not downgraded.
  • After signing out, the back button cannot reopen a sensitive page.
  • Only the small public pages are reachable without signing in at all.
WHEN SOMETHING GOES WRONG

Four questions you'll eventually need answered

Security isn't only about prevention — it's about what you can actually do on the day something happens.

A phone is lost or stolen

Every signed-in pass is on a list. Any one of them can be cut off remotely and immediately — the device is locked out even if it's still switched on.

Someone leaves the organisation

Switching their account off ends their access everywhere at once — every module, every site, every device. There is no second login to remember to close.

"Who changed this, and when?"

The audit log records sign-ins and account changes with the person, the action, the time and the network address. The AI's suggestions are logged separately, including whether a human accepted or overrode each one.

Something needs restoring

The database is backed up automatically by the hosting platform, and the system runs its own scheduled backup job on top of that. Uploaded files sit on storage that survives every software update.

FOLLOW ONE JOB THROUGH

What actually gets written, step by step

A real example: an air conditioner stops cooling in a municipal building. Here is every piece of information the system writes down, and where each piece goes.

01

Someone reports the fault

A ticket record is created, stamped with who reported it, when, which site and which building zone.

→ database
02

They attach a photo of the unit

The picture itself goes to cloud storage. The ticket keeps only a short pointer to it, plus the caption and who uploaded it.

→ photo to cloud storage · pointer to database
03

The AI suggests a priority and a technician

Written to a separate suggestion log — not to the ticket. At this point the ticket itself is completely unchanged.

→ suggestion log, database
04

A supervisor accepts the suggestion

Only now does the ticket change. The log also records that a human accepted it, and which one — so the decision is traceable to a person, not to the software.

→ ticket updated · acceptance recorded
05

The technician uses two parts from the store

Each part becomes its own linked record with quantity and cost, and stock levels drop accordingly. Labour hours are recorded the same way.

→ database, linked to the ticket
06

The job is closed and signed off

A PDF report is generated and filed. The ticket is marked closed — nothing is erased, so the full history stays readable a year later.

→ PDF to document storage · ticket kept

Nothing in this sequence overwrites anything quietly. Each step adds a record rather than replacing one, which is why the audit trail can reconstruct exactly what happened and in which order.

KEEPING IT SAFE

Backups, and what happens to information over time

Automatic daily backups

The hosting platform backs up the entire database on a daily schedule, and the system runs its own scheduled backup job in addition to that.

Files survive every update

Documents and photos sit on storage that is deliberately kept separate from the application, so releasing new software never touches them.

Nothing is quietly deleted

Closed tickets, approved forms and completed reports are kept, not purged. History stays available for audits and for year-on-year comparison.

Your data stays yours

Every module can export what it holds as a spreadsheet or PDF on demand, so the information is never locked inside the system.

HOW AI IS USED — AND KEPT ON A LEASH

Kynvera's AI only ever suggests. A person always says yes or no.

This one rule applies everywhere AI touches the system — there is no exception drawn anywhere else in this document. AI is Anthropic's Claude, the same family of AI used by companies worldwide for this kind of work.

Where AI is actually used

Ticket triage

Suggests priority, a deadline, the best-fit technician, and likely parts needed — from the ticket, the equipment's history, and who's available.

Ticket classification

Suggests which category a new problem belongs to, out of the full fault-code catalog, so nobody has to search it by hand.

Chat assistant

Answers questions using live data across the system, and can draft — never submit — a new ticket or leave request.

Asset intelligence

Predicts which equipment might fail next, and forecasts next quarter's likely budget and spare-parts demand.

Device fleet summary

Writes a one-line health summary of the company's phones and tablets for the admin dashboard.

Chat naming

Titles a new conversation with the assistant automatically, so chat history stays easy to scan.
